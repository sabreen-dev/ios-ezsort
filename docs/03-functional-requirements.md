# Requirements Traceability

## Purpose and authority

This existing filename now owns cross-document coverage mapping only. All functional and nonfunctional definitions, business rules, and acceptance criteria are in [Product Requirements](02-business-requirements.md), the existing equivalent of `02-product-requirements.md`. This separation prevents the old business/functional split from becoming competing sources of truth.

The chain is requirement → UX responsibility → architectural responsibility → implementation milestone → planned automated tests and other verification → recorded evidence. The TST references are plans, not fabricated tests. No implementation or test status has been established.

## Evidence maintenance

When implementation begins, augment verification references with real test names/paths and recorded outcomes. Keep requirement identifiers stable. A scenario may mix automated tests with device or human evaluation; the testing strategy identifies which. Do not mark an entire requirement verified when an open question still blocks an applicable acceptance condition.
